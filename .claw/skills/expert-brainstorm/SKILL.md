# 何时使用

当用户要求从多位专家、多个学派或多个战略视角审视同一议题，并最终落到可执行决策建议时使用。

适合：

- 投资买卖时机判断
- 地缘政治、产业、政策与风险决策
- 需要同时比较乐观、审慎、冲突、合作等不同框架的议题

如果用户只要单一路径的事实总结，优先用 `basic-evidence-scan` 或 `deep-synthesis`。

# 输入约束

- 先确认议题、时间锚点、评估窗口、决策目标和用户约束。
- 如果用户指定了专家、流派或分析框架，优先使用这些视角。
- 如果用户未指定，主动补成 3 到 7 个差异明确的视角，不要堆重复立场。
- 如果使用历史人物、已故学者或知名专家名义，必须把他们当作“理论视角”或“分析框架”，不要伪造原话、私下信息或现实背书。
- 所有判断都要区分“证据支持的事实”和“基于该视角的推演”。

# 工作步骤

1. 先调用 `MemorySearch`，查看当前议题在用户、租户或当前 WebAgent 会话中是否已有稳定定义、关键变量、历史判断或风险边界。
2. 优先从已接入资料获取证据：上传文档用 `SourceSearch` / `SourceRead`，网页用 `SourceWebFetch`，ES 用 `EsSearch`，数据库用 `DbQuery`。
3. 证据不足时，先明确缺口，再做有限度情景推演，不要把推演写成已证实事实。
4. 在正式进入多专家视角前，先输出一段议题澄清：用户到底在问什么决策，时间窗口是什么，哪些变量最关键。
5. 为每位专家或视角分别给出：核心判断、关键逻辑、最看重的信号、对决策的直接含义。
6. 每轮阶段性判断后调用 `TopicDriftCheck`，确保讨论没有滑向人物生平、理论介绍或无关旁枝。
7. 在独立评估之后，组织交叉辩论：只围绕最关键的 2 到 4 个冲突点辩，不要让所有角色彼此泛泛回应。
8. 汇总共识和分歧，并把真正影响决策的冲突点整理成矩阵或结构化列表。
9. 在最终建议中回答三个问题：现在该不该做、什么条件下继续做/暂停、哪些标志性事件会改变判断。
10. 对长期可复用的判断框架、风险触发器和术语口径调用 `MemoryWrite`，不要把整场角色辩论原样写入记忆。

# 输出要求

- 默认按下面结构输出：
  - Phase 0：议题构建
  - Phase 1：多位专家独立评估
  - Phase 2：交叉辩论
  - Phase 3：共识 / 分歧地图
  - Phase 4：综合分析报告与行动建议
- 如果内容较长，优先调用 `ArtifactEmit` 输出一份 `markdown` 报告，标题建议为 `专家会诊 / 综合结论`。
- 每位专家独立分析建议各输出一份 `markdown` 结果卡，标题建议为 `专家视角 / 专家名`。
- 对“共识 / 分歧地图”“风险矩阵”“买入 / 卖出触发条件”优先调用 `ArtifactEmit` 输出 `table`，标题建议为 `专家会诊 / 共识与分歧` 或 `专家会诊 / 风险矩阵`。
- 只有在确实需要表达“立场冲突链路”“因果链”或“联盟 / 对抗关系”时，再输出 `graph`。
- 每位专家视角都应回到用户问题本身，而不是展开成长篇理论综述。
- 最终建议必须给出触发条件、观察指标、风险提示和可能的反转信号。

# 记忆策略

- 当前 WebAgent 会话：当前讨论里的临时假设、未确认冲突点。
- `user`：对该用户同类决策长期有价值的判断框架、风险清单、信号体系。
- `tenant`：跨用户仍成立的通用方法论、术语定义和监测口径。

# 偏题控制

- 如果讨论开始变成“介绍这位专家是谁”，立刻收回到“这个视角对当前决策意味着什么”。
- 如果用户要的是买卖建议、行动方案或政策选择，每一阶段都必须回到“如何决策”。
- 如果证据明显不足，直接标记为高不确定性情景，不要继续扩写成确定性结论。

# 禁止事项

- 普通 WebAgent session 不可用本地文件、shell、grep、glob、read、write、edit 工具；不要要求或假设这些能力可用。
- 专家只可调用平台资料检索、ES、引用、记忆、产物和专家输出相关工具。
- 不要伪造专家原话、访谈内容或现实表态。
- 不要把理论人物写成真的参加了当前会议。
- 不要把内部推演过程当成逐字思考记录暴露给用户。
- 不要只给观点，不给触发条件、反转信号和行动含义。
- 不要展示原始工具返回、后台路径或调试信息。
