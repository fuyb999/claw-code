# Web Agent 原型迁移改造方案

更新时间：2026-05-15

## 新增边界修正：AG UI 与 WebAgent 完全重构

本轮重新确认后，中央聊天区不能继续停留在“旧 thread snapshot / SSE 适配成 assistant-ui 消息”的形态。当前工具调用、检索结果、专家过程和最终答案仍容易被拆成不同气泡，本质原因是前端仍在旧消息块上做兼容合并，而不是让 Agent Run 生命周期成为一等模型。

实施状态：已完成 AG UI 原生端点、AgentTurn 数据库存储、前端 AgentTurnView 主渲染、WebAgent 工具白名单和 `workspace_root` 主链路移除。当前验收地址按运行环境约束使用 screen 启动，运行库固定为 `.clawd-dev/clawd.db`。

验证状态：`cargo fmt`、`cargo test --workspace`、`npm test -- --run`、`npm run build` 已通过；`cargo clippy --workspace --all-targets -- -D warnings` 当前仍被仓库级既有 lint 债阻塞，范围在 `runtime`、`commands`、`api`，不属于本轮 AG UI WebAgent 主线改造。

后续 AG UI 改造采用以下硬边界：

1. **后端直接实现原生 AG UI 协议端点。**
   - 新主链路不再以前端 adapter 把旧 `/v1/threads/:id/events` 转成 AG UI 内部状态
   - Rust 后端新增面向 WebAgent 的 AG UI endpoint，直接输出 run、text、tool/activity、state、error、finish 等事件
   - 旧 SSE 可以在过渡期留作兼容或调试，但不能再作为中央聊天主体验的数据真源

2. **一个用户问题只对应一个 Agent 回答。**
   - 工具调用、ES 检索、专家执行、引用收集、产物生成和最终正文都属于同一个 Agent Turn
   - 不再把 `tool_use`、`tool_result`、专家输出、检索结果拆成多个普通气泡
   - 中央聊天区应渲染 `AgentTurnView` 这类结构化回答，而不是继续把运行过程塞回普通消息列表

3. **过程展示默认产品化，技术细节只给管理员/调试。**
   - 普通用户看到“正在检索资料”“命中 12 篇文档”“Howard-Wang 正在分析”“已生成引用”等可理解步骤
   - 默认隐藏工具名、JSON 参数、原始返回
   - 管理员或开发模式可以展开 AG UI events、tool args、raw result

4. **引用必须从原始 evidence 标记升级为脚注/引用列表。**
   - 正文只显示 `[1] [2]` 等编号
   - 底部统一展示“引用资料”列表，包含资料库、索引、标题、片段、命中信息等
   - `evidence:...#hit-x` 这类内部标记不得直接出现在用户正文

5. **多专家作为同一回答内部的运行态。**
   - 一个用户问题下只有一个 Agent 回答
   - 多专家状态、摘要、引用数、失败/重试和最终汇总都在回答内部展示
   - 专家原文可以折叠查看，但不能恢复为多个刷屏气泡

6. **历史回放必须基于数据库中的规范化 Agent Turn。**
   - 新增 `agent_turns` 作为 WebAgent 历史主表
   - 每轮记录用户输入、助手正文、状态、过程步骤、引用、专家结果、产物、错误/中断原因等结构化字段
   - 可选 `ag_ui_events` 保存原始事件，供管理员调试或审计
   - 刷新页面和历史切换时直接按 `agent_turns` 渲染，不再从散乱 message/tool blocks 临时推断

7. **不迁移旧 JSONL，不兼容旧历史展示。**
   - `.clawd-dev/sessions/*.jsonl` 不再作为新 WebAgent UI 的历史来源
   - 旧 `session_path` 如果短期仍被底层 runtime 需要，只能作为内部执行日志
   - 本轮不做旧 JSONL 到 AgentTurn 的迁移，也不为旧历史投入兼容展示成本

8. **运行中输入不能禁用，采用停止 + 可见队列。**
   - 当前 run 进行时，发送按钮变为停止按钮并显示运行态
   - 用户仍可继续输入，后续问题进入可见“待发送”队列
   - 当前 run 完成后自动发送下一条
   - 点击停止只中断当前 run，不清空队列

9. **时间线采用外层用户时间线 + 内层 Agent 过程线。**
   - 左侧主时间线只给用户问题打圆点
   - 同日显示短时间，跨天插入日期分隔，同年显示“5月15日 周五”，跨年显示“2026年5月15日 周五”
   - Agent 回复不在左侧主时间线打点，而是挂在用户问题下方
   - Agent 内部过程卡片可以有更小圆点，hover 显示完整事件时间和耗时
   - 过程过多时默认折叠为关键步骤，展开后查看细节

10. **WebAgent 主链路彻底去掉 `workspace_root`。**
    - 新 API、前端、AgentTurn、历史列表、管理配置都不暴露、不传递、不显示 `workspace_root`
    - 新对话上下文由 `tenant_id`、`owner_id`、`conversation_id`、资料库选择、个人上传、专家选择、模型配置组成
    - 如果底层执行短期需要目录，只能使用内部临时 sandbox，例如 `.clawd-dev/runtime/<conversation_id>`，不能进入产品 DB 模型或用户心智
    - 原 `workspace` 语义替换为平台资料库、个人上传、当前对话记忆、用户收藏、ES/DB/外部连接器

11. **WebAgent 工具白名单收紧。**
    - 默认保留：`EsSearch`、`SourceSearch`、`SourceRead`、`SourceWebFetch`、`DbQuery`、`MemoryWrite` / memory search、`ArtifactEmit`、`ExpertPanelEmit`
    - 专家 skill 继续可用，但只能调用平台数据工具、资料检索工具、引用工具、记忆工具和产物工具
    - `expert-brainstorm`、`basic-evidence-scan` 等残留 `workspace`、`glob_search`、`grep_search`、`read_file` 的 skill 需要改写
    - `ReadFile`、`WriteFile`、`EditFile`、本地 grep/glob、`Bash`、`PowerShell`、`NotebookEdit`、`TodoWrite`、依赖本地工作目录的 worker 工具不进入 WebAgent 普通用户会话
    - skill 管理从 workspace skill 迁移到平台/租户/用户 skill 语义，后续目标仍是数据库真源

12. **聊天区错误、滚动和过程展示必须重新产品化。**
    - “处理失败 / 处理异常”不能作为全局横幅固定在聊天内容最上方，除非是加载历史或认证失败这类页面级错误
    - 单轮运行失败必须挂到对应的 `AgentTurn` 内，显示在该回答卡片的状态区和失败步骤上，并在输入区提供重试入口
    - 用户发送新消息后必须立即出现用户消息和运行中的 Agent 回答，并自动滚动到最新内容
    - 自动滚动遵循主流聊天产品规则：用户在底部附近、刚发送消息、收到当前 run 首个 token、收到当前 run 完成事件时滚到最新；用户主动滚到历史位置时不强制跳动，只显示右下角“回到最新内容”
    - 工具调用、ES 检索、专家执行和引用收集不能作为独立气泡或页面顶部结果输出，必须挂在当前 Agent 回答内部的过程步骤下
    - 过程步骤默认显示用户可理解摘要，例如“检索 Sina Elasticsearch”“命中 8 篇资料”“Howard Wang 正在分析”；原始 tool args、JSON result、AG UI event 只放进管理员技术细节
    - 每个过程步骤可以展开查看命中摘要、引用编号、耗时、失败原因和重试状态，但不把大段检索结果直接铺在正文上方
    - 最终回答正文与过程区分层：正文持续流式输出，过程卡片同步更新；引用列表固定在该回答底部

这条边界的直接含义是：

- WebAgent 是平台多用户产品，不是浏览器套 CLI workspace
- 中央聊天要从“消息气泡 + 兼容块”升级为“Agent Turn + AG UI 事件流”
- 新历史、运行状态、引用、专家过程和工具过程都要围绕 Agent Turn 建模
- 后续开发计划应优先处理 AG UI endpoint、AgentTurn DB、聊天渲染和去 `workspace_root`，而不是继续局部修补旧气泡

### AG UI 完全重构落地顺序

本轮确认采用“先打通新主链路，再替换旧 UI”的路线，避免继续在旧 SSE / thread snapshot 上做局部修补。

1. **数据库主模型先行。**
   - 新增 `conversations` / `agent_turns` / 可选 `ag_ui_events`
   - 新 WebAgent 历史、刷新回放、对话列表都以 DB 为准
   - 不迁移旧 JSONL，不为旧 session 历史做兼容适配

2. **后端新增原生 AG UI endpoint。**
   - 新 endpoint 直接面向 WebAgent 会话
   - 输出 run、text delta、activity/tool、citation、expert、state、error、finish 等事件
   - 事件写入 `agent_turns`，原始事件可选写入 `ag_ui_events`

3. **前端新增 `AgentTurnView` 主渲染。**
   - 中央聊天不再以散乱 message bubble 作为主模型
   - 每轮用户问题渲染一个完整 Agent 回答
   - 流式正文、过程卡片、专家折叠、引用列表、技术详情都在同一 turn 内

4. **工具、引用、专家过程统一映射。**
   - `EsSearch` / `SourceSearch` / `DbQuery` 等工具映射为用户可读过程步骤
   - 引用统一转为脚注编号和底部引用列表
   - 多专家结果不再刷成多个普通气泡

5. **去除 WebAgent API 和前端中的 `workspace_root`。**
   - 新建对话、历史回放、资料选择、专家运行都不再需要 `workspace_root`
   - 内部临时 sandbox 只能留在后端实现细节
   - 旧 thread/session/workspace 字段不进入新 WebAgent 前端类型和用户文案

6. **收紧管理员配置与工具白名单。**
   - 普通用户只消费已发布模型、资料库、ES/DB 源和专家
   - 管理员维护平台配置，配置真源仍是数据库
   - WebAgent 普通会话默认不暴露本地文件、命令、编辑、worker 类 CLI 工具

每一步都必须能独立编译和验收。禁止先大规模重写前端外观但继续依赖旧事件模型；也禁止先清理全部 Rust runtime 导致长时间没有可验收的聊天主链路。

### AG UI 主链路阶段状态：2026-05-15

本阶段已推进到“DB-backed AgentTurn 主渲染 + AG UI runtime 接线”：

- 后端已提供 `/v1/agent/conversations`、`/v1/agent/conversations/:id/turns`、`/v1/agent/conversations/:id/interrupt`、`/v1/agent/ag-ui`，并补充 `DELETE /v1/agent/conversations/:id` 用于删除 WebAgent 历史会话。
- `agent_conversations` / `agent_turns` 已作为新历史真源；删除会话时同步清理该会话下的 turns。
- 前端新增 `useWebAgentSession`，由 WebAgent conversation id 作为 AG UI `threadId` 调用后端原生 endpoint，流式 text/activity/state/result 合并为 `AgentTurnRecord`。
- `ConversationStage` 在收到 `agentTurns` 时走 `AgentTurnView` 主路径，旧 `ThreadPrimitive` 只保留为过渡回退，不再作为 `InspirationMode` 的中央聊天主数据源。
- `InspirationMode` 的对话列表、发送、中断、删除已切到 WebAgent conversation/turn 主线；资料、专家、模型选择作为 AG UI run/conversation 选项传入，不再从新主线传递 `workspace_root`。
- 已验证：`npm test -- --run src/components/conversation/ConversationStage.test.tsx src/components/conversation/AgentTurnView.test.tsx src/lib/clawd/agent-turns.test.ts`、`npm run build`、`cargo test -p clawd ag_ui`、`cargo test -p clawd agent_turn`、`cargo test -p clawd sqlite_store_round_trips_agent_conversations_and_turns`、`cargo check -p clawd`。

剩余边界：

- `InspirationMode` 仍临时保留旧 thread 派生的研究摘要/右侧专家运行状态作为过渡展示，下一阶段需要把 `ResearchBrief` / `ResearchTask` 从 `AgentTurnRecord` 派生，彻底移除中央聊天对旧 thread snapshot/SSE 的依赖。
- 后端 runtime 内部仍会创建受管临时 thread/session 以复用现有执行引擎；这是内部实现细节，不得回流到 WebAgent API、前端类型或用户文案。
- Runtime `TOOL_CALL_RESULT` 目前仍缺少 provider 原始 `tool_call_id` 精确关联，后续需要在 `ToolExecutor::execute` 链路补入 tool call id。

### 聊天区产品化补充：2026-05-16

本轮再次检查真实页面后，确认当前 AG UI 主链路虽然已经把工具、检索和引用事件接入 `AgentTurn`，但表现层仍有三个不成熟问题：

- 失败信息仍可能以页面级横幅出现在聊天内容顶部，和具体失败轮次脱节
- 发送消息后没有稳定滚动到最新消息位置，用户需要手动找刚刚发出的内容
- 工具调用、检索步骤、执行结果虽然已进入过程区，但还没有形成“步骤 -> 子结果 -> 引用/调试”的产品层级，容易看起来像把日志换了皮肤

新的聊天区设计边界如下：

1. **错误归属到 turn，不上浮到聊天顶部。**
   - `useWebAgentSession.error` 只用于列表加载、认证、网络整体不可用等页面级错误
   - run 内错误写入 `AgentTurnRecord.error` 和失败步骤，`AgentTurnView` 在对应回答内展示
   - 输入区只显示“上条发送失败 / 可重试”的轻提示，不再把失败内容插到消息列表最上方

2. **滚动策略以用户意图为准。**
   - 发送成功创建本地 turn 后立即滚到底部
   - 当前 run 的首个文本 delta、activity snapshot、run finished 都触发“若用户在底部附近则跟随滚动”
   - 用户手动向上查看历史后停止自动跟随，只显示浮层按钮
   - 该按钮固定在聊天内容右下、输入框上方，不占用单独一行

3. **过程展示采用嵌套步骤，而不是平铺日志。**
   - `AgentActivityTimeline` 从纯 flat list 升级为“阶段卡片 + 子步骤”
   - 检索阶段下展示数据源、查询词、命中数量、引用编号和失败/空结果状态
   - 工具阶段下展示工具用途和结果摘要；普通用户不看原始 JSON
   - 专家阶段下展示每个专家的运行状态、摘要、引用数和重试状态
   - 管理员展开技术细节时，才显示 AG UI events、tool args、raw result

4. **正文、过程、引用三层固定。**
   - 正文区只承载最终回答和流式文本
   - 过程区承载检索、工具、专家、产物状态
   - 引用区承载 `[1] [2]` 对应资料列表
   - `evidence:...#hit-x`、tool result 原文和内部状态机文案不得进入正文

该补充不改变“一个用户问题对应一个 AgentTurn”的主模型，只要求前端展示和后端 step payload 更接近成熟 WebAgent 产品。

## 运行环境约束补充：2026-05-14

本仓库在当前执行环境下，普通 `nohup ... &` 或简单 shell 后台化并不稳定，服务进程可能在命令会话结束后被回收。因此后续凡是需要交付“可验收的本地前后端地址”，统一增加以下运行约束：

1. **长驻前后端进程必须使用独立会话托管。**
   - 优先使用 `screen`
   - 不再把普通 `nohup` 视为可靠后台方案

2. **启动后必须立即做存活校验。**
   - `lsof -iTCP:<port> -sTCP:LISTEN -n -P`
   - `curl http://127.0.0.1:<port>/healthz`
   - `curl -I http://127.0.0.1:<port>/`

3. **本项目当前验证通过的启动方式如下。**
   - 后端：
     - `screen -dmS clawd-webagent ...clawd`
     - 需要显式设置 `CLAWD_WEB_DIST_DIR=/.../webagent-ui/dist`
     - 需要显式设置 `CLAWD_DATA_DIR=/Users/fuyb/IdeaProjects/claw-code/.worktrees/webagent-route1/.clawd-dev`
     - 当前这条路线只允许使用 `.clawd-dev/clawd.db` 作为运行库
   - 前端预览：
     - `screen -dmS webagent-preview npm run preview -- --host 127.0.0.1 --port 4173`

4. **交付验收地址时必须同时给出日志位置。**
   - `.logs/clawd.log`
   - `.logs/webagent-ui-preview.log`

5. **管理员配置验收必须基于后台持久化结果，而不是表单回显。**
   - 模型配置、资料空间、平台 ES 资料库必须通过后端 API 成功写入后再视为完成
   - 页面刷新后仍能回显，才算验收通过

6. **本地验收管理员账号必须固定纳入平台管理员列表。**
   - 当前本地默认开发账号为 `admin`，验收账号还包含 `admin-check`
   - 后端 screen 启动时必须显式设置：
     - `CLAWD_PLATFORM_ADMIN_USERS=admin,local-dev,admin-check`
   - 如果遗漏 `admin-check`，`/v1/auth/session?user_id=admin-check` 会返回 `is_platform_admin=false`，管理视图会读不到平台级模型配置、资料空间和 ES 资料库
   - 如果没有接入 OIDC，前端不再展示开发用户输入框，默认使用 `admin` 直接进入主界面
   - 修改启动参数后必须确认没有旧的孤儿 `clawd` 进程继续占用 `3210`，必要时先停止旧进程再重启 screen

7. **管理员配置必须写入平台作用域。**
   - 管理员创建的模型配置承载项目、资料空间、ES 资料源必须保存为 `owner_id = NULL`
   - 普通用户创建或上传的个人资料仍保存为用户自己的 `owner_id`
   - 管理员只能读取平台作用域配置；如果误用非管理员账号写入，会变成个人配置，其他管理员看不到

8. **开发模式历史配置归并策略必须固定。**
   - 当未接入 OIDC 且启用开发头部鉴权时，系统启动阶段会自动把历史开发身份写入的“配置型记录”归并到平台作用域，确保默认 `admin` 可直接看到之前已配置的数据
   - 归并范围仅包括：
     - 模型配置承载项目
     - 非上传型资料源，例如 ES / Web / Git / DB 等
     - 与这些资料源关联的资料库
     - 平台连接器配置
   - 归并范围明确**不包括**上传型个人资料文件与个人上传资料源，避免把用户私有上传自动提升为平台共享资料
   - 这条规则是开发模式兼容策略，不改变正式 OIDC 多用户隔离边界

9. **启动前必须确认当前运行库。**
   - 在 `.worktrees/webagent-route1` 下，`clawd` 当前验证使用的是 `.clawd-dev/clawd.db`
   - 旧库 `.clawd/clawd.db` 只用于回收历史平台配置，不作为当前运行库
   - 启动前如果 `lsof` 显示 3210 对应的不是 `.clawd-dev/clawd.db`，必须先停旧进程再启动

## 新增边界修正：管理员配置承载层

本轮实现再确认后，需要补一条产品与实现边界，避免新前端继续泄漏旧概念：

## 新增边界修正：管理员配置必须持久化

2. **普通用户不可编辑。**
   - 普通用户只能使用管理员已发布的模型、资料源和专家技能

   - 普通用户主工作台只读取管理员发布后的可用配置，不承担配置录入职责

4. **数据库是配置真源。**
   - 环境变量可以提供默认值或启动时兜底，但不是长期配置真源
   - 后续前端管理页、后端 API 和启动逻辑都应以数据库记录为准

这条边界的直接含义是：

- 当前 `webagent-ui` 中与模型、资料源、技能相关的设置入口，需要重新区分“普通用户可见摘要”和“管理员可编辑配置”
- 后端需要补或确认对应的数据库 schema、读写 API 和权限控制
- 前端中的浏览器模型表单只能作为开发兼容路径，不能被当作正式产品配置模型

## 主流 WebAgent 迁移原则：2026-05-13

本轮再次确认后，迁移不再参考旧 `web/` 的 UI 组织方式。旧 `web/` 只提供能力清单和技术合同，例如 API、SSE、消息结构、artifact/evidence 渲染、错误状态和运行状态。新产品的信息架构必须来自新的 `AI 分析师` 原型，并按主流 WebAgent 的用户心智重新放置能力。

主流 WebAgent 的共同做法可以抽象为：

1. **登录后的 workspace/project 是长期上下文。**
   - 用户进入的是自己的工作空间，而不是选择本地目录。
   - 对话、上传、收藏、产物和私有研究材料都归属当前用户。
   - 后续可以扩展 shared project、成员、角色和可见范围，但第一阶段先保证个人隔离。

2. **左侧承载资料上下文。**
   - 我的上传、我的收藏、平台资料源和当前资料范围都在左侧。
   - 对话切换和新建放在中央聊天顶部，避免左侧被历史列表挤占。
   - 用户看到的是“资料”“来源”“收藏”“平台知识”，不是 `workspace_root`、ES endpoint、index 或认证参数。
   - ES 是平台已发布的数据源，普通用户只搜索和选择，不配置连接。

3. **中央对话/时间线是唯一主工作流。**
   - 用户直接提问，不需要先进入“灵感 / 数据 / 任务”三页。
   - 系统根据问题自动触发专家讨论、资料检索、引用选择、综合回答和写作产物。
   - 检索事件、专家消息、失败/重试、引用、artifact、表格、图表、报告草稿都出现在中央时间线。
   - 多任务并行时，中央顶部提供“对话列表”和“进行中总览”，但不把历史列表迁回左栏。

4. **右侧只放当前任务的能力控制。**
   - 对本项目而言，右侧就是专家控制面板：专家选择、讨论模式、自动检索、并发、重试和运行状态。
   - 不恢复旧 `web` 的右侧 workbench、results/evidence/timeline tabs。
   - 证据详情、artifact 预览和 source snippet 从中央时间线打开局部 sheet/detail，而不是占用常驻右栏。

5. **管理能力低频化、角色化。**
   - 普通用户路径继续保持低频设置，但模型、ES、资料库和技能配置本身属于管理员视图，不是普通用户设置项。
   - 普通用户可以看到管理员发布后的摘要和选择结果，但不能编辑底层配置。
   - 技能/专家管理、模型配置和资料接入配置都应进入独立管理员视图，并写入数据库。
   - 普通用户路径不出现 ES 连接、内部 skill runtime、服务器路径等后台信息。

因此本次 UI 迁移采用 **A + C** 路线：

- **A：原型原生重映射。** 保留新原型的顶栏、左资料/历史、中时间线、右专家控制三栏结构。
- **C：时间线优先。** 将旧 `web` 的结果、证据、过程、artifact 能力迁移为中央时间线事件和上下文详情层。
- **B：轻量管理抽屉只作为例外。** 仅用于模型设置、账号设置等低频动作，不能成为新的控制台主路径。

   - “灵感 / 数据 / 任务”应融合为 `AI 分析师` 内部能力：专家讨论、资料检索、写作执行由 Agent 自动协调，并在中央时间线可见

6. **旧 `web` UI 不再作为布局参考。**
   - 不迁移旧 `web` 的抽屉式管理结构、右侧 workbench、results/evidence/timeline tab 结构或控制台启动页
   - 旧 `web` 的功能必须先转换成“用户能力”，再放入新原型的合适区域
   - 每个迁移项都要能回答：它属于左侧上下文、中央时间线、右侧专家控制，还是低频设置

## 原型适配分析

### 原型里值得继承的部分

参考原型的这些组件，方向是对的：

- `AppShell`
  - 顶栏 + 左侧上下文 + 中央工作区
- `InspirationMode`
  - 左历史 / 中对话 / 右专家 的三栏结构
- `HistoryPanel`
  - 会话历史与资料放在一个稳定侧栏里
- `ChatPanel`
  - 中央持续对话，不依赖额外页面跳转
- `ExpertPanel`
  - 专家树、勾选、多专家参与模式

这些都和当前 Web Agent 目标高度匹配。

### 原型里不能直接照搬的部分

原型不是当前项目可直接合入的前端实现，原因很具体：

- 原型是另一套应用壳和状态模型，不是基于当前 `assistant-ui` 会话链路
- 原型假定 `灵感 / 数据 / 任务` 三种模式切换，但当前 Web Agent 主路径应该是单主舞台
- 原型没有承接当前仓库已有的 `artifact / evidence / audit / model config / data source` 真正运行能力
- 原型更像前端演示样机，而当前仓库已经是可运行的多用户 Web Agent 服务

所以本次方案的原则是：

- 迁移布局、交互层次和视觉语言
- 保留当前后端 API、SSE、专家编排、资料接入、结果渲染
- 拒绝做一次高风险的整页代码替换

## 目标产品定义

### 新的产品定位

当前 `web/` 应收敛为：

“一个聊天优先的 Web Agent 工作台，支持资料接入、专家会诊、结构化结果与来源追踪。”

### 非目标

本轮不做：

- 完整复刻原型中的三模式研究操作系统
- 把分屏模式作为第一阶段主架构
- 收藏中心、全局飞轮、命令面板的完整产品化
- 新增一套脱离当前后端的专家执行引擎
- 为了迁移原型而重写所有前端 API 层

左侧栏接管当前“设置抽屉”中最常用的用户入口，直接成为常驻主导航。

建议固定为资料上下文，不再兼任对话历史。

- 当前资料范围
- 我的上传
- 我的收藏
- 平台资料源

### 3. 中央 Conversation Stage

中央区域必须成为唯一主舞台。

核心原则：

- 默认进入页面就是聊天
- 聊天内容滚动，输入区固定
- 首屏欢迎态轻量，不再像控制台启动页
- 消息气泡按内容自适应，不由外层容器强行撑高
- 用户消息、助手消息、专家消息有稳定层次
- 本轮步骤挂在回答下方，不再变成消息瀑布
- 引用、结果、来源从消息直接打开上下文详情 sheet / modal，不占用右侧专家栏

中央区的组成建议：

- 当前对话标题与轻量上下文条
- 对话列表入口
- 进行中总览入口
- 消息列表
- 本轮产出摘要
- 固定输入区
- 附件/资料快捷区
- 任务边界与重规划入口内嵌在 composer 区域

对话列表的结构建议：

- `进行中`
- `最近查看`
- `已完成`

- 标题
- 一行副标题
- 状态

### 4. 右侧 Expert Control Rail

原型右侧是 `ExpertPanel`。新原型迁移后，右侧仍然只承担专家控制职责，不再把旧 `web` 的结果、来源、过程 workbench 搬进右侧主栏。

建议右侧主结构：

- 讨论模式
- 专家树
- 已选专家 chips
- 会诊参数
  - 并发数
  - 重试次数
  - 是否自动检索
- 当前轮专家状态摘要

结果、来源、过程不进入右栏 tab。它们应该作为中央聊天时间线的一部分呈现：

- 每个专家完成后生成一条独立专家消息
- 专家失败并重试耗尽后生成一条失败专家消息
- 最终综合结论生成一条助手综合消息
- 引用、证据、结果卡、写作大纲和正文都挂在中央消息或研究任务流中
- 需要展开时使用 sheet / popover / detail panel，而不是常驻右栏 workbench

这避免右栏同时承载专家选择和结果工作区，保持新原型页面的产品心智稳定。

### 4.1 AI 分析师融合式工作流

原型的“灵感 / 数据 / 任务”分屏表达了一个正确目标：讨论结果可以引用到数据，数据结果可以进入写作任务。但原型实现主要是并排窗格和本地 cross-reference 状态，不足以支撑成熟 WebAgent 的持久工作流。

迁移后的主路径应把三种方式融合到 `AI 分析师` 标签下：

- `灵感`：多专家讨论、观点生成、问题拆解、复评
- `数据`：ES 检索、个人上传资料检索、证据引用、结果分析
- `任务`：写作、整理、执行、产出文档

用户不需要手动切换三种模式。Agent 根据问题自动调度能力，并允许能力之间相互跳转：专家讨论发现缺证据时自动检索资料，检索结果回到专家复评，综合结论再转入写作任务。过程在中央时间线可见，用户可以随时干预，例如“只讨论不写作”“先查资料”“用这些证据重写”。

第一阶段需要保留一个轻量 `ResearchTask` / `ResearchBrief` 边界，让专家讨论、证据引用和写作产物挂到同一线程/研究任务下。分屏可以后续作为辅助预览或引用对照能力回来，但不作为主产品结构。

当前实现先落一个更薄的 `WebAgentExecutionIntent` 边界：中间聊天输入仍是唯一主入口，发送时根据是否已选专家、是否存在资料范围、自动检索开关和问题措辞，自动选择 `expert_panel`、`retrieval_augmented_chat` 或 `plain_chat`。这只是融合式调度的第一层，不恢复“灵感 / 数据 / 任务”页面入口；后续 `ResearchTask` / `ResearchBrief` 应在这个意图边界上扩展，而不是重新引入三模式主导航。

Phase 5 第一段已落地前端派生型 `ResearchBrief`：它从当前线程的中央时间线事件中汇总用户问题、资料范围、检索次数、专家观点、综合结论和产物数量，并在聊天顶部显示“研究简报”。这不是独立任务页，也不改变后端 schema；它先提供一个稳定的研究状态边界，让用户可以继续输入“只讨论不写作”“先查资料”“用这些证据重写”等干预指令，后续再把写作任务和持久 `ResearchTask` 挂到该边界上。这里的“写作整理”阶段已经收紧为显式写作意图边界，只有当线程里出现“整理为报告”或“基于证据重写”这类明确指令时才进入，不再因为普通 artifact 自动升级。

在此基础上，当前又补了一层轻量 `ResearchTask`：前端仍保留基于 `research_stage` 时间线的派生逻辑，但后端已经开始把可见研究状态以 `research_task_state` audit record 的形式持久化到线程审计流中。前端读取时优先采用这条持久状态，缺失时再回退到派生逻辑。`writing_ready` 当前与 `run_started.prompt` 中的显式写作指令对齐，而不是和 artifact 数量直接绑定。它依旧不是独立任务页，也还没有完整写作执行闭环；当前作用是先把“下一步该做什么”显式化，并为后续写作任务、自动复评和跨端恢复提供稳定边界。

### 5. 管理与用户操作分离

必须继续贯彻此前已经在做的方向：

- 用户面只看聊天、资料、专家、结果
- 管理面才看模型、技能、资料接入配置、资料库策略
- operator console 继续保持独立 surface

因此：

- “设置”只放普通用户常用设置和入口
- “资料接入与技能”进入独立管理员视图
- “模型配置”进入独立管理员视图
- 管理页不再默认出现在主视图
- 模型、ES、资料库和技能配置都必须通过数据库持久化，不能依赖前端临时状态

用户看见的应当是：

- 分析视角
- 专家组
- 讨论方式
- 已选专家

而不是：

- skill 名称
- scope
- runtime 提示词
- tool 契约

### 推荐交互

1. 用户在右侧 `视角` 栏勾选专家

## 性能与稳定性要求

这次重构必须顺手解决当前“勾选专家后发起会疯狂占用浏览器资源”的风险点。

### 重点风险

- 大量 state 堆在 `App.tsx`，任何局部交互都可能引起整页重渲染
- 专家会诊的 run 事件、artifact、audit 同时更新，容易触发重复计算
- 聊天区、右栏、抽屉共用同一层 state，视图切换成本过高

### 处理原则

- 左栏、聊天区、专家控制栏拆成独立组件并使用稳定 props
- 专家状态摘要和中央时间线派生数据尽量走 `useMemo`
- 继续过滤内部工具输出，不把大段原始 JSON 推给消息区
- 详情 sheet 未打开时不做重型渲染
- 图表、关系图和大表格延迟渲染

## 后端依赖评估

### 第一阶段需要新增或稳定后端能力

当前后端已经有线程、资料源、skills、artifact/evidence/audit 和旧 expert panel 编排基础，但第一阶段要形成成熟多人 WebAgent，还需要稳定以下能力：

- 线程列表与线程详情
- OIDC 登录、回调、登出和当前用户 session
- 专用 expert panel run API
- expert panel run SSE
- 每个专家独立 skill / 独立模型调用
- 专家失败重试和并发控制
- artifact / evidence / audit
- 独立模型配置
- 资料库与数据源接入

### 第二阶段可选增强

为了让前端更像成熟产品，后续可以考虑补这些后端增强，但不是迁移阻塞项：

- 专家 skill 返回更多展示元数据
- 线程摘要字段，减少左栏自行推导成本
- 上传进度事件
- 更轻量的“用户过程记录”接口，而不是继续直接从 audit 聚合

## 重新对齐后的主线推进

基于本轮边界修正，当前前端主线应按下面顺序继续，而不是再围绕单点切换控件做局部优化：

1. **文案去技术化**
   - 中央主舞台、运行状态、列表标题和空态全面去掉“会话 / 线程 / session / thread”表达
   - 用户面统一收敛到“对话 / 进行中 / 最近查看 / 已完成 / 失败”

2. **中央顶部升级为对话列表**
   - 将现有可搜索切换面板升级为按状态分组的“对话列表”
   - 列表分为“进行中 / 最近查看 / 已完成”
   - 每条对话显示标题、副标题、更新时间、状态和简要计数

3. **补“进行中总览”轻入口**
   - 在中央顶部或顶栏提供“进行中 N”入口
   - 支持在多个同时执行中的对话之间快速跳转

4. **统一三栏滚动与 sticky 边界**
   - 左右栏各自滚动
   - 中间头部与输入区保持稳定
   - 中央消息区作为主滚动区域

5. **再回到多任务细节体验**
   - 进行中状态提醒
   - 已完成/失败的快速回看
   - 对话列表中的排序、搜索和轻量筛选

## 视觉与交互原则

本次界面不应再像“控制台”或“后台表单页”。

应遵循这些视觉原则：

- 中央留白优先
- 顶栏轻而窄
- 左右栏信息密度高于中央，但不喧宾夺主
- 主按钮数量少
- 卡片圆角、边框、阴影统一
- 不把所有信息都装进重玻璃态大卡片
- 聊天气泡按内容自然收缩，不要整块大框

## 验收标准

迁移完成后，至少满足以下体验：

1. 用户进入页面后，第一眼看到的是中央聊天，而不是设置或抽屉说明。
2. 用户能在中央顶部新建/切换会话，并在左侧查看当前资料上下文。
3. 用户能在右侧直接勾选专家，再在中央发起专家会诊。
4. 每位专家以独立消息进入中央时间线，最后生成综合结论。
5. 用户能直接上传资料或查看来源状态，而不需要理解服务器路径。
6. 模型设置是独立入口，且不和任务创建强绑定。
7. 纯聊天模式不依赖 ES 或资料库。
8. 页面不暴露 `workspace_root`、服务器路径、内部 skill runtime 细节。
9. 浏览器在专家会诊运行中不会因为 UI 自身重渲染而异常占用资源。
10. `AI 分析师` 能在同一线程/研究任务内自动协调专家讨论、资料检索和写作任务，不要求用户切换三模式页面。

## 推荐实施顺序

如果直接进入开发，建议按下面顺序推进：

1. 先做壳层和区域拆分
2. 再做中央聊天改造
3. 再做左栏会话/资料区
4. 再做多专家 skill 会诊和右侧专家控制
5. 再做 AI 分析师融合式研究/写作工作流
6. 最后把低频管理能力收束为设置体系

不要反过来先改样式细节，否则会继续在旧结构上补丁式迭代。

## 与现有主线的关系

这份方案不是新分支需求，而是当前 `web-agent-service-plan` 的前端产品化延续。

它直接承接以下既有方向：

- 弱化路径心智，强化资料库/数据源心智
- 聊天优先
- 专家会诊产品化
- 结果/来源/过程进入中央时间线和研究任务流
- AI 分析师融合式能力调度
- 管理与用户界面分离

因此，后续前端主线改造应以本文件为准，而不是继续在当前抽屉式布局上零散打补丁。
